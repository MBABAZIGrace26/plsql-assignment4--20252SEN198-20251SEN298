# Implementation and Performance Notes

## Design
- 5 core tables with PK, FK, UNIQUE and CHECK constraints (marks 0-100, credits 1-6, valid status,
  one enrollment per student/course/semester).
- Business rules live in procedures: course capacity, active-status check, graded enrollments cannot be dropped.
- Expected business errors use RAISE_APPLICATION_ERROR (-20001 to -20120). Unexpected errors are logged
  and re-raised, never swallowed. Functions never return a fake value.
- Procedures do not COMMIT: the caller controls the transaction. benchmark_bulk_vs_loop uses an
  autonomous transaction so its rollback never affects the caller.

## Records
print_transcript uses a user-defined record (t_transcript_rec) and students%ROWTYPE.
register_student_course and update_marks use %ROWTYPE records.

## Collections
Nested tables t_id_list and t_name_list are schema-level types, so they work as parameters, return values
and in TABLE() queries. Associative arrays and a VARRAY are used in course_grade_report;
associative arrays are also used in the benchmark.

## Cursors
Implicit: SQL%ROWCOUNT, SQL%FOUND and SQL%NOTFOUND after INSERT, UPDATE and DELETE.
Explicit: a parameterised cursor with OPEN/FETCH/CLOSE (with %ISOPEN cleanup) and a cursor FOR loop.

## Bulk processing and performance
A row-by-row loop sends one SQL statement per row, so PL/SQL and SQL engines switch context on every
iteration. BULK COLLECT fetches all rows into a collection in one switch, and FORALL sends the whole
collection of DML in one switch. Fewer context switches means less CPU and round-trip overhead, so
bulk processing is much faster for large row counts.

Bulk errors: FORALL ... SAVE EXCEPTIONS continues after a failing row and raises ORA-24381 at the end.
We read SQL%BULK_EXCEPTIONS (ERROR_INDEX, ERROR_CODE) to report each failed row. Successful rows stay
in the transaction and the caller decides to commit or roll back.

Memory: for very large tables, BULK COLLECT should use LIMIT to process in batches and cap memory use.

## Limitations
The capacity check is count-then-insert, so two sessions at the same time could exceed capacity.
Production code would lock the course row with SELECT ... FOR UPDATE.
